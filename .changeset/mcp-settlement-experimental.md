Add `agents/experimental/mcp-settlement` — a `withMcpSettlement(Agent)` mixin providing durable, hibernation-safe per-server MCP readiness/timeout/cancel callbacks via `watchMcpServerSettled` / `cancelMcpSettlementWatch`. The callback fires durably on the connection-owning DO through the alarm scheduler and is re-derived on wake; cross-DO fan-out stays an app concern.

Also makes the underlying `MCPClientManager` notifications general-purpose and adds a durable, pollable connection-state snapshot (the poll-on-wake enabler for consumer DOs):

- `onServerStateChanged` now emits an `MCPServerStateChange` payload (`{ serverId, url, state, error? }`, widened from `void` — additive for existing handlers that ignore the argument). `state` is a `MCPConnectionState`, the terminal `"removed"` sentinel, or `null` when a still-registered server is downgraded to no live connection (close / failed RPC restore / id-migration with no connection); the event fires on that downgrade too, so awake subscribers (`broadcastMcpServers`, a consumer DO's `publish`) refresh off a stale `ready` instead of only the durable snapshot being updated. The new `onServerRemoved` event (fired with the last-known `{ serverId, url }` immediately _after_ the storage row is removed, so a broadcast subscriber re-reading storage observes the deletion) is the canonical removal signal.
- **Behavior change on removal:** `removeServer` now _also_ fires a terminal `onServerStateChanged` carrying the sentinel `state: "removed"` (a payload-only value — not an `MCPConnectionState`, so the connection FSM, snapshot, and settlement targets are unaffected). This restores the pre-existing contract whereby a subscriber to `onServerStateChanged` alone is notified on removal; without it, such subscribers would silently miss deletions. `onServerRemoved` is fired unconditionally so a serverId-targeted matcher is cancelled even when the last-known url is unknown.
- New durable `{ state, error }` snapshot per server, readable without a live transport probe via `getPersistedServerState()` / `listPersistedServerStates()`. `state` includes `"authenticating"` — derived from a pending OAuth `auth_url`, including a `registerServer({ authUrl })` with a live (default `connecting`) connection, and as a read-time fallback for servers that have no snapshot row yet (e.g. an agent upgraded with a pending OAuth flow). The snapshot is **level-triggered**: consumers apply the latest state idempotently (no version cursor), so removal simply deletes the row and id migration repopulates the new id from live state. Stored in a lazily-created `cf_agents_mcp_server_state` sibling table (no schema-version bump). Without a cursor there are no tombstones or orphan-prune machinery to carry.
- New `onServerIdMigrated` event (`{ oldId, newId }`), fired by `migrateServerId` after the rename and before the post-migration state notification, so serverId-keyed subscribers (e.g. settlement watches) follow a rename instead of stranding state under the old id. A `{ serverId }` settlement watch is now re-targeted across a migration rather than hanging to its deadline.

Wake re-derivation for the settlement mixin runs via an internal, awaited `MCPClientManager.registerPostRestoreHook` / `_runPostRestoreHooks` seam (invoked by the owning Agent after both HTTP/OAuth and RPC MCP restore, before user `onStart`) rather than a generic Agent wake hook — so experimental settlement code does not add a generic extensibility API to stable core, and recovery (which re-arms the durable deadline / at-least-once delivery drivers) is awaited rather than fire-and-forget.

API:

- `watchMcpServerSettled` takes a **required** `deadlineSeconds` (seconds, matching `this.schedule()`'s native unit). Requiring it guarantees the abandoned-OAuth case always resolves and gives every watch a self-cleaning terminal path, so a live intent row can never leak. The deadline is **authoritative**: if it elapses before a watched state is reached, the watch settles as `timeout` rather than a late `settled` (consistent across the awake fast-path and wake re-derivation). The `timeout` result reports `deadlineSeconds`.

Hardening:

- **Closing a connection refreshes its durable snapshot.** `closeConnection` / `closeAllConnections` (without removing the server) now re-resolve the persisted `{ state }`, so a poll-on-wake consumer no longer reads a stale `ready` for a connection that was closed.
- **Delivery scheduling no longer has a lost-callback window.** A settled watch now inserts (and records) its callback schedule _before_ cancelling the deadline alarm, so there is always an armed alarm across every `await` boundary — an eviction can no longer leave a watch terminal-but-undelivered with no alarm to wake recovery. The awake-path delivery is also anchored with `ctx.waitUntil` so the runtime keeps the DO alive until the schedule lands.
- **A same-key retry repairs an unarmed deadline in-session.** If a registration persisted the live intent but crashed before arming its deadline, a later `watchMcpServerSettled` with the same `idempotencyKey` now re-arms the deadline from the intent's original `deadline_at` (idempotent; an already-elapsed deadline fires immediately) instead of relying solely on the next wake — load-bearing for abandoned-OAuth watches, where the deadline alarm is the only wake source.
- **MCP connection restore is now isolated per server.** A single corrupt/unreadable row (e.g. unparseable `server_options`) no longer aborts restore for the remaining servers, and the failed server's durable snapshot is downgraded off any stale `ready` value so a cross-DO consumer polling after wake doesn't read a connection that was never restored. Settlement recovery still runs regardless (a backstop guard remains in the Agent wake path).
- **RPC MCP restore now matches that isolation + downgrade.** `_restoreRpcMcpServers` now wraps each server (including the `server_options` parse) in a per-row try, and downgrades the durable snapshot off a stale `ready` when the binding is missing (a deploy renamed/removed it), the options are corrupt, or the reconnect throws — via a new `@internal MCPClientManager.notifyServerStateChanged(serverId)` seam. Previously a failed RPC restore left `getPersistedServerState()` serving a `ready` row for a connection that no longer existed.
- **`deadlineSeconds` is capped at 30 days.** A live intent row stays `live` for the whole deadline window (polluting live-intent queries on every state change and wake), so `watchMcpServerSettled` now rejects a `deadlineSeconds` greater than 2,592,000.
- **Wake re-derivation no longer scans every intent row.** `rederiveSettlementIntents` now queries only the rows it can act on (`status = 'live'` plus terminal-but-unscheduled), instead of `SELECT *`, so a DO that wakes on every request doesn't pay O(total_intents) while terminal rows wait out their 24h TTL. Added partial indexes on `status = 'live'` and `server_id`, and recovery now re-arms deliveries/deadlines concurrently (`Promise.allSettled`) rather than serially, so user `onStart` isn't delayed by the sum of every outstanding watch's schedule round-trip.
- The per-transition state chokepoint and snapshot getters now resolve the server config row via an indexed single-row lookup (`WHERE id = ?`) instead of a full-table `getServersFromStorage()` scan — the hot path paid by every MCP agent on every state change (wakes produce transition storms).
- **An immediate (already-matching) settle keeps an armed alarm too.** When the target server is already in a watched state at registration, the deadline alarm is now armed _before_ the terminal decision is recorded (the store inserts a live row and defers settling to the mixin), so the always-an-armed-alarm invariant also covers the immediate-settle path. Previously this path armed no deadline, so an eviction between recording the terminal row and scheduling the delivery left the callback with no alarm to wake recovery.
- **Wake recovery waits for in-flight reconnects before falling through to a deadline.** `restoreConnectionsFromStorage` starts reconnects in the background without awaiting them, so wake re-derivation initially observes `connecting`. Recovery now anchors a bounded `waitForConnections()` (capped at 10s, which covers the default per-server retry budget) via `ctx.waitUntil` and re-derives once the reconnects settle — so a watch settles on the real `ready`/`failed` transition instead of timing out when the owner woke only for recovery and would otherwise hibernate before the in-memory transition fired.
- **URL-targeted watches match the server that actually changed.** A watch keyed by `url` now settles when _any_ server sharing that URL reaches a target state (evaluating the changed server first), instead of always re-resolving to the first stored server with that URL — so when duplicate-URL servers settle in different orders the watch no longer stays live or attributes the wrong server. Likewise, removing one of several duplicate-URL servers no longer cancels a URL watch while another matching server remains.
- **Wake recovery re-arms deadlines before settling.** `_recoverMcpSettlementIntents` now re-arms live deadlines _before_ re-deriving/settling, so a registration that crashed after inserting the live intent but before recording its `deadline_schedule_id` (no armed alarm) gets its deadline armed first. Otherwise recovery could settle an already-matching server, then be evicted before the delivery schedule landed, leaving a terminal-but-undelivered intent with no alarm to wake redelivery (the re-arm pass skips terminal rows).
- **A closing connection refreshes its snapshot even when `close()` rejects.** The durable-snapshot refresh in `closeConnection` now runs in the `finally` (after the in-memory connection is torn down), so a rejecting `close()` no longer leaves `cf_agents_mcp_server_state` at `ready` for a connection that was actually cleaned up.
